# npm 下载量归因：6,570/月 的主体是镜像同步，不是使用

## 决定性证据：版本分布

`last-week` 共 729 次下载，分布在 **154 个版本中的 154 个**——即每一个曾发布过的版本，
包括 4 月的 `0.9.1`..`0.9.38`，一周内每个都被下载 1-2 次。

| 分组 | 下载 | 占比 |
|---|---|---|
| 近期 8 个版本（0.66.0..0.69.0） | 531 | 72.8% |
| 其余 146 个历史版本 | 198 | 27.2%，平均 **1.36 次/版本** |

真实用户不会在一周内把 38 个 `0.9.x` 版本各拉一遍。「每个历史版本恰好 1-3 次」是
全量镜像同步（cnpm/yarn mirror 类）与安全扫描器的签名。

近期 8 个版本内部也不成立：`0.68.2`（8-17 发，这一周只有前 5 天是 latest）拿 157 次，
高于当前 latest `0.69.0` 的 134 次。真实使用流会让 latest 持续累积，实测是发布脉冲后归零。

## 佐证一：有下载为 0 的日子

97 天区间（05-20..08-24）合计 18,884 次，**中位数 54/天，均值 195/天，最大 1,490，最小 0**。
0 下载的日子：`2026-06-05` `2026-06-27` `2026-07-12` `2026-08-14` `2026-08-24`（当日数据未收完）。
日均 220 的真实用户群不会有整天零下载。极度尖峰（均值是中位数的 3.6 倍）是脉冲，不是流量。

## 佐证二：发布密度与下载量不相关

发布日（26 天）均值 387，非发布日（71 天）均值 124——看似相关，但逐日对齐后不成立：

| 日期 | 当日 tag 数 | 下载 |
|---|---|---|
| 2026-05-21 | 13 | 16 |
| 2026-05-24 | 10 | 32 |
| 2026-07-12 | 4 | **0** |
| 2026-07-10 | 10 | **1,490** |
| 2026-08-12 | 0 | 894 |

下载量最高的 10 天里 7 天不是发布日。5-6 月高密度发布几乎不产生下载，7 月起同密度发布
下载暴涨——变化的不是发布行为，是这个包在 7 月被某个全量同步源收录了。

## 结论

冻结记忆的判断不变：**没有第三方采用证据**。npm 数字不构成反证，GitHub 侧 0 issues / 0 forks
与之一致。定位（personal harness, fork-and-adapt not turnkey）仍然准确，不需要改。

推论：以「外部用户会受益」为理由的工作项，前提不成立。剩余工作只应按**维护者自用价值**
和**收敛止损**排序，不按覆盖面或对称性排序。

## 重估触发条件

出现下面任一条再重新评估，而不是按「下载量涨了」重开：

- 任何一个 issue / fork / 可辨认为非作者的 star。
- 版本分布形状翻转：历史版本长尾归零，而 latest 在发布后**持续**累积（真实使用的签名）。
- 出现单日 >200 且当天无发布、**次日仍 >100** 的连续段（脉冲与流量的区分点）。
