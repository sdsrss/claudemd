## 7 同日执行记录：用模拟与历史数据代替等待，六项决策

使用者的意见：批 3 不必等评估窗口，"可以在沙箱模拟测试，或者分析以往的会话数据"。这个意见成立，理由是逐个窗口核对的结果：

- **D#72**：主指标是会话级**首次**触发率。首次触发之前模型还没见过 hook 文案，所以改文案动不了主指标。
- **D#58**：只有 M1、M3 两个指标（被拒之后的行为）受文案影响。它们本来就适合用"同一条命令、只换文案"的配对比较来测，这正是 PREREG 第 5 节说的因果方法，而且比前后对比更干净。M2、S1 与文案无关，窗口照常。
- **G1b**：它是否值得给模型看，可以用历史回合直接回放判定器来估精确率，不需要先让它在真实会话里跑 30 天。

下面四个实验的脚本和数据都存在本地 `tasks/`（该目录不进 git），给出的是路径。

### 7.1 实验一：rm 拒绝文案的离线配对 A/B（F2）

- **语料**：从全部转录抽取 675 次 rm 拒绝，排除测试闸门时的夹具命令后剩 424 条。按项目分层抽 60 条（seed 20260926）。
- **方法**：同一条命令分别配现行文案（A，平均 1,764 字符）和新文案（平均 922 字符），交给 `claude-opus-5-5`。调用方式：`claude -p`，无工具，无会话持久化，`--setting-sources ""`（不加载插件、不写遥测），附 core 规范。让模型给出下一条命令，再用本仓库的真实钩子在沙箱 HOME 里判定。
- **结果**：

| | A（现行） | B（新文案，初版） | B′（调整语序后，即提交版） |
|---|---|---|---|
| 重试命令放行，且保留原目标、未自发加令牌 | 57/60 | 59/60 | 59/60 |
| 自发加 `[allow-…]` 或 `DISABLE_*` | 0 | 0 | 0 |
| 每次拒绝的输入 token（均值） | 14,348 | 13,927 | 13,954 |

- **判读**：
  - A 失败的两条，一条把变量删除改成了字面路径，一条把删除改成了 dry-run；第三条是三臂都没通过的同一个复杂命令。
  - 只有一方对的配对，A 对 B 为 0 : 2。
  - 结论是非劣。样本天花板很高（A 已 95%），所以不声称"更好"。
- **调整语序的原因**：现有测试 `msg-order` 钉住"对裸 `$TMPDIR`，先说'照那一行修'，再给加守卫的建议"，否则 `rm -rf "${TMPDIR:?}"` 会放行并删掉整个临时目录。B 初版把这句放在末尾，测试报红，于是调整语序后重测，得到 B′。
- **花费**：两轮 $5.46。
- **局限**：离线模拟里模型只看到命令和拒绝消息，没有会话上下文。
- **执行**：`616ab20`。D#58 PREREG 已追加修订：M1、M3 的窗口在该版本暴露时截止。
- **数据**：`tasks/d57-rm-gate-eval/ab-2026-09-26/`。

## 8 对照 Anthropic《Prompting Claude Opus 5.5》：规范要不要随模型升级

使用者的问题：模型升到 Opus 5.5，Anthropic 也发了 5.5 的提示词指南，全局规范要不要跟着升级、优化或精简？

### 8.1 结论

**不需要为 5.5 重写，也不需要大幅精简。** 官方原话："Existing Claude Opus 5 prompts should perform well without changes"。5.5 指南共 11 节，大部分是 API 和运行环境层面的内容（effort 档位、thinking 不能关、进度更新改走 thinking 块、标记粘贴内容、看图工具、前端默认风格），能作用到 Claude Code 里这份规范文本的只有少数几条。

真正该改的是 Opus 4.x 时期写下、方向与官方现行指导相反的两三处。它们和"升到 5.5"本身关系不大，5.5 文档只是加强了改的理由。

### 8.2 逐条对照

| 官方指南 | 出处 | 规范对应处 | 判断 |
|---|---|---|---|
| 5.5 会在多步长任务中途用文字结束回合：一段总结，宣布下一步却不做。官方给了一段系统提示样例，点名四种不要的停法，并点名允许的停法（没有用户就无法推进，或受保护的东西挡住了） | 5.5 §Unattended agentic runs | core §11 "Mid-SPINE turn-yield (HARD)" | **方向一致，保留。** 5.5 比以前更需要它。可改进的是写法：现行文字用 SPINE / VALIDATE 等内部术语，官方写法直接描述"哪些停法不要、哪些可以"。官方说这段不适合有人在场的应用，本仓库是交互式，但 `AUTONOMY_LEVEL: aggressive`，而且 §11 的 "Tell" 条款记录了使用者对中途停下的反感 |

1. **§EXT §11-O 委派默认值**：按官方抑制样例重写，同时把"独立评审"收窄到发版前和 L3，即批 2 的 M1 扩大一点范围。证据最足：本地 43.1%，加上 Opus 5 和 best practices 两份官方指南。原计划等 G2 窗口；按 7.5，可以改在隔离 worktree 里用固定任务集做 headless 对照，成本由使用者决定。

## 9 发版前评审子代理的耗时与成本

使用者的问题：每次发版评审，后台子代理要跑半小时以上，有的超过一小时，token 在 200k 以上，还要跑三遍。这正常吗？是 skill 的问题还是 Claude 的问题？在不降低质量的前提下怎么提速？

### 9.1 结论

**不是 skill 的问题，本仓库的发版评审没有用任何 skill。** `gs:/review` 在本机没有注册（第 0 节第 3 条），所以按 §EXT §12 技能路由表 review 行的兜底，评审一直是"空上下文子代理 + 作者手写的评审说明"。时长和成本由三件事决定：§12 的评审要求（证伪、每条附复现、列出 `NOT CHECKED`）、评审说明的写法，以及模型的思考量。换 skill 解决不了主要问题：内置 `/code-review` 和 `matt:code-review` 查的是 diff 的正确性，而本仓库发版被卡住的主要是"陈述超出代码"（9.3）。

"其他用户是不是也这样"答不了，没有数据。能给的只有同仓库对照：`sp:subagent-driven-development` 的逐任务评审中位 1.6 分钟。

- **极端样本**：`apreship-0880`（09-13）167.7 分钟，其中 49.6 分钟在跑测试，全量套件跑了 5 次，每次 6.5～8.3 分钟。09-25 有一个 Opus 5.5 评审跑了 103.4 分钟，其中 81.9 分钟在用 `sleep 580/590` 等自己启动的后台任务。它一个就占了 Opus 5.5 组 120 分钟 sleep 中的 82 分钟。
- **口径说明**：具名组用 transcript 文件名匹配（脚本里的 `REVIEWER`），09-22 以后的子代理没有具名，所以没进这一组。"测试执行"匹配 `npm test/check/smoke`、`run-all.sh`、`node --test`、`bash tests/…`；"全量套件"只匹配 `npm test/check` 和 `run-all.sh`。时间按 tool_use 到 tool_result 的时间戳差计算。
- **混杂因素**：`~/.claude/settings.json` 的 `modelSettings` 把 `claude-opus-5` 设为 `xhigh`，`claude-opus-5-5` 设为 `high`。如果子代理沿用这项设置（没有核实），09-22 之前的具名组跑在 Opus 5 `xhigh`，和 Opus 5.5 那一列的差别不能只归因于模型。

### 9.3 为什么要跑三轮

轮数来自 §EXT §12 Review-finding repair 的 Resume 条款：修复后对修复提交重审，深度上限 2。推高轮数的主要是陈述类缺陷：

- v0.88.0 预发评审五轮：代码行为缺陷 0（909 条命令差分 `verdict_diffs=0`），所有阻断项都是 CHANGELOG、注释、提交说明里的数字或说法超出代码实际（claude-mem #210）。
- 两次发版的陈述类发现中，13 条里有 7 条是**修复提交自己引入的**（记忆 `feedback_repair_commit_breaks_the_docs_it_repairs`）。第二、三轮多半在审上一轮修复带来的新问题。
- 发版频率把次数放大：22 天 28 个 tag（ship runbook 记忆，2026-09-26 分析 B9）。

评审的价值有记录：v0.77.0 连续几轮各出一个 High，最后撤回了轮转重设计（#34）；v0.78.0 抓到"本次发版的测试是假的"和"三条回退路线都不通"两个 Critical。所以要去掉的是浪费，评审本身不砍。

### 9.6 需要使用者同意的事项：逐项建议

判断原则：**不改变评审检查什么**的改动（去掉重复和等待），用论证加现有数据就可以同意；**改变检查什么或由谁来检查**的改动（分级、换模型、降 effort），必须先有检出率数据；数据由 9.7 的离线重放产生，不用真实发版去试。

补充的两项实测（本轮新做）：

- **全量重跑有没有产出过发现**：65 个具名评审共执行 135 条全量套件命令，13 条输出带失败标记。逐条看：多数是文本误匹配（例如 `grep` 到 `run-all.sh` 里的 `FAIL` 字样）。真正变红的几次：`apretag-delta` 在主检出目录里读到了作者未提交的改动，它自己的报告也写明已提交的树 `npm run lint` 为 0；`apretag-code` 在改了 `TMPDIR` 的工作树里跑出一条 CJK 失败，报告没有把它列为发现；`ar16-hooks` 和 `ar630-review` 属于审计轮，不是发版评审。**没有找到一次全量重跑变成针对发版范围的发现。** 局限：失败是按输出里的标记识别的，被 `tail -2` 截掉标记的失败会漏计。
- **补丁版不一定低风险**：v0.76.2 是一次修复批次的补丁版，它的预发评审抓到一个 Critical：`stat -c %s F || stat -f %z F || echo 0` 并不是可靠的 GNU/BSD 兼容写法，在 hook 的 `set -u` 下会让 shell 退出，把一条不可豁免的 §8 `rm -rf` 拒绝变成放行（记忆 `project-audit-docs-local-only`）。所以"`fix:` 发版就轻审"有反例，不能用。

| D5 | R5：降 effort 或换 Sonnet | **同意做 9.7 的离线重放，只比 Opus 5.5 `high` 和 `medium` 两组；Sonnet 暂缓** | 73% 的时间在模型生成，effort 是最直接的杠杆；Anthropic 的 5.5 指南说 `medium` 在编码评测上达到或超过 Opus 5 的 `high`（第 8 节）。但评审是找缺陷，不是写代码，那组评测结果不能直接套用，所以要测。只比两组，是为了在同样的花费下让每组样本多一些 | 批准约 44 次评审运行的花费（9.7） |

| D7 | R7：内置 `/code-review` | **不做** | 它查的是 diff 正确性，本仓库发版被卡住的主要是陈述类问题；再加一条评审路线，流程会更复杂。只有 9.7 的结果显示代码类发现占多数时再考虑 | 无 |

**D1 为什么用 agent 定义，不继续手写说明**：现在每次发版都手写评审说明，65 个具名评审的首条消息长度从 2,540 到 7,513 字符不等，要求每次都不完全一样，结果也就没法比。Agent 工具的说明写明，agent 定义的 frontmatter 决定它的 model、reasoning effort 和可用工具；把固定部分写进定义，每次只传入提交范围和"待证伪的说法"清单。D5 的结果也就只需要改这一个文件。frontmatter 里 effort 的字段名，落地时按 Claude Code 文档确认。

**D1 定义里写入的规则**（草案）：

1. 说明里给出被评审的 SHA，以及该 SHA 的 CI run id，或者作者对该 SHA 跑 `npm run check` 的退出码（修复提交还没推送时用后者）。**不要为了确认而重跑全量套件。**
2. 允许跑测试的两种情况：为复现某条发现跑单个测试文件；或者在**与 CI 不同的条件**下跑（换 `TMPDIR` 所在的文件系统、并发、`HOME` 布局），并先写明要验证的假设。第二种对应记忆 `feedback_green_on_tmpfs_red_on_ext4`，这类问题 CI 抓不到。
3. 在隔离的 worktree 里工作（runbook 步骤 7 已有要求），不读主检出目录。`apretag-delta` 那次变红，就是因为读到了主检出目录里作者未提交的改动。
4. 单条命令在前台运行，加 `timeout`。Bash 工具前台上限 600 秒；需要更久的实验不要放到后台再 sleep 等，改成缩小样本，或者把命令写进 `NOT CHECKED` 交给作者去跑。作者可以让出回合等后台任务，评审子代理结束回合就等于结束任务。
5. 不设硬性的工具调用上限：没有数据说明发现集中在前多少次调用里，硬上限可能截掉后面才出现的发现。先按 9.7 记录每条发现出现在第几次调用，再决定要不要设。

### 9.7 评估方案（预注册）

**A. D1 上线后的效果（观察式，真实发版）**

- 起点：第一次使用 `release-reviewer` 定义的发版。基线：`subagent-cost.mjs` 在上线前一天的输出，保存到 `tasks/`，之后不再改。
- 主要指标：每个 tag 的评审总分钟数；每个评审的全量套件执行次数（预期中位 1 → 0）；sleep 分钟数（预期接近 0）。
- 质量护栏：每次发版的 Critical/High 条数单独记录。条数下降本身不说明问题（也可能是代码更好了），所以另看**逃逸缺陷**：发版后 14 天内，修复该发版改动内容的 `fix:` 提交数，与上线前 14 个 tag 比较。
- 样本：具名组 p90 是中位的 4 倍，分布很偏，所以用中位数和每 tag 的合计，不用均值；至少攒够 10 个 tag 再下结论。

**B. D5 的离线重放（对照实验）**

- **题目**：已知评审抓到过 Critical/High、且事后修复的提交范围，用修复前的 SHA。候选：v0.76.2 的 `stat` 链、v0.78.0 的"测试是关键词闸门"和"三条回退路线不通"、v0.77.0 轮转重设计的四个 High、v0.88.0 的陈述类问题。从中选 4 个，外加 1 个干净范围（评审没有 Critical/High、此后 14 天没有针对它的修复），用来量误报。误报也会增加轮数。
- **组别**：Opus 5.5 `high`（对照，即现状）与 Opus 5.5 `medium`。说明模板相同（D1 定义），只改 effort。
- **样本量**：每组 4 个题目 × 5 次 = 20 次，另加干净范围每组 2 次，共约 44 次。
- **检验力**（精确计算，Fisher 单侧，α=0.1，对照检出率按 0.9 假设）：每组 20 次时，检出率降到 0.6 能测出的概率约 0.75，降到 0.5 约 0.91，降到 0.7 只有约 0.48，降到 0.8 约 0.20。也就是说，**这个规模只能排除大幅下降，不能证明两组一样好**。要把 0.9 → 0.7 测出来（检验力 0.8），每组约需 45～50 次。
- **判定规则**（跑之前定死）：`medium` 被采用，需要同时满足：(1) 汇总检出率不低于对照减 0.10；(2) 没有任何一个题目出现对照 ≥4/5、`medium` ≤2/5 的情况；(3) 干净范围上的误报 High 不多于对照；(4) 墙钟中位至少下降 25%。满足时，结论写成"没有观察到大幅下降"，不写成"质量相同"。
- **防泄漏**：重放必须让评审看不到答案。(a) 用 `git archive <sha>` 导出到项目路径以外的新目录，没有之后的提交历史，CHANGELOG 里也不会出现事后的修复；(b) 新目录不属于本项目，claude-mem 的 PreToolUse 召回和项目记忆不会把当年的教训注入进去，这一点要在第一次运行时检查 transcript 确认；(c) 说明里不写题目名称和版本号。
- **评分**：由一个不知道组别的评分子代理，或者按预先写好的匹配规则（文件 + 机制，行号允许偏差）把每次的发现和标准答案对照；每次运行记录发现出现在第几次工具调用，供 9.6 D1 第 5 条使用。
- **花费估算**：Opus 5.5 子代理计费输入中位 8.7M（9.2），44 次约 3.8 亿，多数按缓存读计价；输出约 44 × 46k ≈ 200 万。按次数算，相当于 09-05～09-22 期间约 12 天的正常评审量（18 天 65 个具名评审）。
- **顺序**：D1 先落地，重放用 D1 的说明模板，结论才适用于以后的发版。

**同意后的执行顺序**：D1 → D3 → 按 A 观察 → D5 离线重放 → 视结果改 D1 定义的 effort → D4 → 数字成立后再提 D2（规范改动，需净删除）。D6 从下一次发版开始执行。
