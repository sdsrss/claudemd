#### ENG-02 · P2 · **已修复（2026-09-05 23:05，未提交）** · `memory-read-check.sh` 标签匹配前的引号剥离仍是两遍 sed，混合引号会吞掉中间整段命令，§11 deny 静默丢失

- **位置**：`hooks/memory-read-check.sh:125-128`（`sanitize_for_tagmatch`：`sed -E 's/"[^"]*"/""/g' | sed -E "s/'[^']*'/''/g"`）。同文件 :94 的 trigger 阶段已改用共享的单遍状态机 `hook_trigger_view`，`hooks/lib/hook-common.sh:573-591` 写明两遍 sed「把一个区域的闭合引号和下一个区域的开引号配对，删掉中间的命令」正是 R11-05 修掉的缺陷；此处是同一缺陷的残留副本。
- **证据（对同一 sed 管道的探针 + 共享 awk 的对照）**：
  - 输入 `grep 'a"b' f && ship runbook && grep 'c"d' g`：两遍 sed 输出 `grep '' g`；单遍 awk 输出 `grep '' f && ship runbook && grep '' g`。剥离后文本中 `runbook` 出现次数：sed 版 **0**。
  - 输入 `echo 'it"s' && git push origin main --tags && echo "don't" release`：sed 版 `echo ''t" release`，push 段整段消失；awk 版保留。
- **影响**：trigger 阶段仍能识别 `ship`/`git push`（它用的是正确实现），所以 hook 会进入标签匹配；但 `CMD_TAGMATCH` 里目标词已被吞掉 → `memtags_match` 无匹配 → `exit 0`，**不落 fail-open 行**。结果是 HARD 门在恰好该拦的命令上放行且不可观测。触发条件是同一命令里同时出现两种引号且各含对方引号字符——`grep 'a"b'`、`echo "don't"` 这类形状在 agent 生成的 shell 里并不罕见。方向是漏拦（fail-open），不是误拦。

## 11.7 Q-01 定性与由此发现的 P1（2026-09-05 23:37，工作区未提交）

### 11.7.1 复现方法（全程沙箱，HOME 重定向，从未指向 `~/.claude`）

两个探针，脚本在 `$TMPDIR/…/scratchpad/q01/`（本轮已随会话清理）：

- **探针 A（机制）**：把生产分支照抄一份，在年龄检查与 `rmdir` 之间注入 `sleep 0.2`；窗口内由另一进程 `rmdir` + `mkdir` 取得新锁。比对锁目录 inode。结果：`stale inode=4087541 fresh inode=4087542`，B 的 `rmdir` 退出 0 且**新锁消失**——回收者删掉了别人刚拿到的锁。
- **探针 B（端到端，自然窗口，无注入）**：沙箱 HOME + `CLAUDEMD_LOG_MAX_MB=1` + 1,220,000 B 的超阈日志，`.1` 预置 `GEN1-MARKER`，4 个**真实进程**并发调用出厂 `rule_hits_append`。判据无需在临界区插桩：一次轮转 ⇒ `.2` 是 `GEN1-MARKER`；两次轮转 ⇒ 第二次的 `mv .1 .2` 把刚归档的 live 代覆盖上去，`.2` 变成 live 代且 `.1` 消失——正是 P1-1 注释描述的 `{live,.1,.2} → {gone,gone,live-as-.2}`。

### 11.7.3 主因与修复

`hooks/lib/rule-hits.sh`：授权轮转的 size 检查在 `mkdir` 互斥体**之外**。P2 在日志仍超阈时读到 size，P1 完成轮转并释放锁，P2 的 `mkdir` 于是**成功**，对一个已经轮转过的日志再跑一遍两步 `mv`：`mv .1 .2` 把 P1 刚归档的 live 代盖到 `.2`，`mv log .1` 因日志已不存在而静默失败。ROT-1 用例全程持锁，按构造只能走到 `mkdir` 失败那条臂，所以两轮审计都没看到。

**改动（+27 / −2，1 个源文件）**：在 `mkdir` 成功后**重读一次 size**，由这一次决定是否轮转。第二个持锁者读到的日志要么不存在（`stat` → 0）要么已在阈值下，于是什么都不做。

**新增用例 ROT-6**（`tests/hooks/rule-hits.test.sh`，确定性，仿 ROT-4 的 `find` 垫片手法）：一个计数式 `stat` 垫片让**第一次** size 查询返回超阈值、之后如实返回——这正是 P2 的状态。RED 控制：`git stash push -- hooks/lib/rule-hits.sh` 后该用例报 `FAIL: ROT-6 .1 rotated on a stale size reading:` 并打出被覆盖进 `.1` 的 live 行。

### 11.7.4 Q-01 的处置：残留，已评估接受

主因修掉后，Q-01 的残留窗口收窄到「B 删掉 D 的新锁 → E 取得锁 → D 与 E 都在各自完成第一个 `mv` 之前通过了互斥体内的 size 检查」，实测 8/400（仅在预置陈旧锁时）。

**报告提议的 `mv "$lock" "$lock.reap.$$" && rmdir` 无效，且是实测而非推断**：同一夹具 6/400，与现状的 8/400 无统计差异。原因：`rename(2)` 的原子性针对**移动动作**，不针对**被移动对象的身份**——晚到的回收者照样会把一个新锁搬走，与 `rmdir` 删掉它是同一回事。报告里「只有一个回收者能成功，失败者不会碰到别人的新锁」这句话不成立。

真正能关闭的做法：用一次 rename 原子地「认领」live 代（`mv "$log_file" "$log_file.rotating.$$"` 后再归档），使同一代日志只可能被一个进程拥有。**本轮不做**：它引入新的孤儿类（进程在认领与归档之间被杀会留下 `*.rotating.<pid>`），需要配套回收器，而这条路径两天内已经改过三次。残留代价是归档遥测，不涉及任何门的判定或用户数据。以上连同测量数字已写进 `rule-hits.sh` 回收分支的注释，标记为「已评估接受，无新证据勿重提」。
