#### 6.1 FLW-H1 — 泄漏的 `install.lock` 让同步 bootstrap "报成功、装了空气"，持续 10 分钟，无任何提示

`scripts/install.js:168-183`：锁被占 → 返回 `spec:"skipped-locked"`，**exit 0**。
`hooks/session-start-check.sh:833-846`：exit 0 → `hook_install_sentinel_clear`、读用户内容横幅、记录 `bootstrap-sync`、`exit 0`。
node 首次启动超过 4 秒被 `platform_timeout` SIGTERM 掐掉时没有 `finally`，锁留下；同一轮的 detached 重试（`:853`）和之后 10 分钟内（`INSTALL_LOCK_STALE_MS`）每个 SessionStart 都静默 stand down。

**lead 复核**：两段源码逐行确认。r17-flows 沙箱实测（J6b/J6c/J9a）：三个会话 rc 0、stdout 空、manifest 与 spec 均不存在；先前的 `bootstrap-failed.json` 出了一条"Retrying this session"横幅，然后被一次什么都没装的运行清掉。`docs/flows/bootstrap.md` 第 17 步与 `ARCHITECTURE.md:137` 的"never worse than the async path"在这个分支上为假。

**受影响者**：冷 NFS/APFS home、AV 扫描、高负载笔记本——恰是同步路径存在的理由（`:795-823`）所要照顾的用户。

**修法方向**：(a) `install.js` 在 bootstrap 场景下对 `skipped-locked` 返回非零（如 3）或机器可读标记，hook 据此不清哨兵、不记 `bootstrap-sync`；(b) `acquireInstallLock` 对记录 `pid` 已死（`process.kill(pid,0)` → ESRCH）的锁立即视为过期；(c) 同步分支在上次运行为 `skipped-locked` 时自行写失败哨兵。

#### 6.2 SCR-H1 — 过期锁接管是 TOCTOU，两个并发安装可同时进入锁窗口

`scripts/install.js:144-165`：锁超过 10 分钟 → `stat → unlink → claim`。两个进程同时 stat 到同一个过期锁，A unlink + claim 成功，B 的 unlink 删掉 A 刚建的锁，B 的 `open('wx')` 也成功。前提（残留锁）正是 6.1 的产物；竞争双方正是 SessionStart bootstrap 与 UserPromptSubmit 的 piggy-back。后果回到 Round 14 修锁前的失败：两者都先读 `existing`，用户内容 home 上败者的 `createBackup` 找不到东西，返回一个空的最新 `backup-*`，而 `CLAUDEMD_SPEC_ACTION=restore` 读的正是它。

**证据**（r17-scripts，40 次并发，锁 `touch -d` 老化 20 分钟）：`both-fresh(double-holder)=1 skipped-locked=18 serial=21 / 40`。**lead 复核**：源码逐行确认三步序列。

**修法方向**：用原子 rename 接管——`rename(lock, lock + '.stale.' + pid)` 只会有一个赢家，然后 `claim()`；仍 EEXIST 则返回 null。补一个老化锁 + 并发的测试（`install.test.js` 目前只测并发 fresh，从不老化锁 → SCR-L7）。

#### 6.3 HK-H1 — §11 记忆闸门读不到子代理的 transcript，而它现在就在一层目录之下

`hooks/lib/hook-common.sh:253-258`（`hook_memfile_was_read` grep `"file_path":"<memfile>"`）、`hooks/memory-read-check.sh:225`（`TRANSCRIPT=…/${SESSION_ID}.jsonl`）。

### 8.2 总判决

**达到"纪律性护栏工具"的生产级——对 Linux + jq + Node ≥ 20 + GNU coreutils 的用户，且以 5 条 High 在下一个 tag 前关闭为条件。**

**未达到的两块**：(1) 原生 macOS——README 与 `platform.sh` 互相矛盾，CI 从未跑过无 coreutils 路径，实测看门狗只约束单进程；在此之前 README 的"必须装 coreutils"是唯一有证据的契约，应保留。(2) marketplace 渠道的发布闸门——推 tag 即发布，pre-tag 只有 runbook 的自我约束（R16 M2 仍开）；这不是本轮新发现，但 ROLLBACK.md 把它写成已有控制，是本轮新的。

**本轮最该记住的不是任何单条，而是一个重复形状**：`skipped-locked` exit 0、`--help` 说保留、CHANGELOG 说 exit 0、ROLLBACK.md 说有等待、README:66 说无备份、advisory 说"没有输出"、core:91 要求报出不许调用的技能——**七处文本比代码多说了一步，而守它们的测试钉的是别的东西**。这与记忆层 `feedback_repair_commit_breaks_the_docs_it_repairs` 和 #108（"代码从第一个提交起就对，阻断项全是陈述"）是同一件事。修 High 时请用整行 golden pin 钉替换后的句子，不要只删旧句。

### 12.1 偏离本报告自己开的方子（四处）

1. **§9 第 1 条要求「修前在 worktree 量父提交基线，40 次并发 1 次双持有者 → 目标 0/40」——没做这个测量。** 换成把落败者的 `statSync`/`readFileSync` 冻结到它观察到的那一刻再跑真实代码路径：竞争窗口是微秒级，一个 1/40 命中率的用例当闸门太弱（它有 39/40 的概率绿着放过回归）。代价是没有「0/40」这个数字，报告里的 1/40 仍是修前的唯一定量。
2. **SCR-H1 的方子（`rename` 接管）单独不成立。** rename 只解决两个同时接管者的情形；晚到的接管者面对的是赢家**新建**的锁，rename 照样搬得走。真正封口的是「搬走的必须就是我判过期的那个文件」这一身份校验。
3. **而 inode 不是身份。** 第一版按 inode+dev 校验，tmpfs 上 57/57 绿、ext4 上红：赢家 `rmSync` 释放的 inode 被它自己的 `open(wx)` 原样拿回来。最终按**字节 + mtime + inode/dev** 四项判定，两个文件系统各跑一遍。这条是修复过程自己产生的缺陷，按本仓库惯例单独成提交（`9c78288`）而不是 amend 掉。
4. **HK-H1 放宽了判定，报告原文对此存疑。** §6.3 写「未追：子代理的 Read 是否应算作父会话之后 push 的凭证（大概率不应）」。实现选择了算——理由写在谓词头部：另一条路是让规范强制的评审角色面对一条无合规解的 HARD deny。这是一次判断，不是一次推导。
