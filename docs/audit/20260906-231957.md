## 2. 四个问题的直接回答

### 2.1 "版本有点久，有没有适应模型能力提升？"

**日期上不老，结构上老。** changelog 从 v6.9.2（2026-04-21）到 v6.26.0（2026-09-06）共 51 个版本、4.5 个月，平均 2.7 天一版；v6.25.0（08-09）已做过一次压缩，之后 5 个版本又涨回 95.8%。这种节奏下累积的是"防误读补丁"，而当前模型（Claude 5 系）对短声明式规则的遵从已明显好于这些补丁所针对的行为——本仓库 30 天采样：§11 turn-yield 0/41、§10-V 0/346、四段式 0/6 违规（§3.6）。

具体过时假设（§5 详述）：
1. 把 "clarification of clarification" 写进 core（`§0 Hard-AUTH override` 之外又有 `§5 Obvious-follow-on not exempt (clarifies §0 …)`；§11 turn-yield 的 Tell 判据；§2.1 "Skill MUST wording does NOT override"）——这些是为模型把规则读歪时打的补丁。
2. 子代理交付机制用了 4 处、约 2.5 KB 记录一次 2026-09-06 的实测，而 harness 系统提示已用一句话陈述同一事实（"Subagents run in the background; you'll be notified when one completes"）。
3. 路由表只认插件 skill（`sp:dispatching-parallel-agents`），不提 harness 原生 `Agent`（含 fork）/ `Workflow` 原语；`TaskOutput` 已弃用仍在 §11-O 出现。
4. §11 Post-compaction 要求 "Re-Read plan + spec"，而 core 由 harness 每 turn 注入，重读 core 是纯浪费（约 7 k token）；上一轮 SPEC-M5 已指出，未改。

### 2.2 "是否以 spec 为基础、规范化、智能化、自动化？"

### 2.3 "有没有分散注意力、占过多上下文？"

**结论**：core 占常驻指令的主体，但 token 成本本身不是瓶颈（prompt cache 下边际成本低，OPERATOR §13.1 与 2026-07-10 优化方案 B3 均已如此判断）。真正的注意力代价在两处：

1. **密度**：core 每非空行均 144 B，最长行 1 261 B（§11 turn-yield，core:239）；86 处 ≥15 字符的括号插入合计 3 818 B（16%）；123 个 `§` 交叉引用、32 个 `→ §EXT` 指针。读者要在一行里同时处理规则、例外、例外的例外和指针。
2. **重复 / 冲突指令**：与 harness 系统提示重叠约 1.5–2 KB（§4），其中两条**直接冲突**（报告范例用括号 + 破折号，harness 禁止；§0 默认 ASK vs harness "proceed without asking"）。冲突段每次写报告都要在两套风格指南间裁决，这是比字节数更实在的注意力损耗。

**hook 侧不构成注意力负担**：4 个 PreToolUse hook 单次 7–8 ms，正常路径注入 0 字节；Stop 五个 hook 合计约 86 ms（§3.4）。

### 2.4 "有没有冗余需要优化？"

有，且 spec 违反了自己的 "one home per fact"。可净删除的冗余清单见 §6，合计估算 core −3.0 KB、extended −2.3 KB；另有约 0.8 KB 应从 core **移入**（`aggressive` 跳过清单）而非删除。

## 5. 模型能力提升后已过时的设计假设

1. **"模型会把规则读歪，所以要写澄清"**：core 有 3 处 "clarifies …" 式条款、1 处 "Two bullets below carry a stronger tag" 元说明、1 处 Tell 判据；采样 0/41 与 0/346 说明当前模型不需要这些拐杖。删除它们不改变任何规则语义。
2. **"模型看不懂指针，所以指针要带解释"**：core:60 "a core citation without a §EXT pointer is a defect" 是维护者的规则，写在 Agent 每 turn 读的 core 里。移 OPERATOR。
3. **"事故要写进规则才记得住"**：§11 turn-yield 内嵌 "measured 2026-09-06"、§11-O 内嵌 "3h02m / 126 tool calls / 230 ms"。当前 harness 已把该事实写进系统提示；规则只需说 "yield 即交付"，理由归 changelog（§13 META 本来就是这么分工的）。
4. **"子代理是插件功能"**：§2.1 / §4 / §11-O / §12 只以 sp/gs skill 命名并行与评审；harness 原生 `Agent` 带 fork、后台运行与完成回调，`Workflow` 提供确定性编排。规范应把原语写为主路径，skill 写为封装。
5. **"上下文是稀缺资源，所以要预算字节"**：25 K / 50 K 硬上限本身仍有价值，但理由应从 "占上下文" 改为 "稀释指令跟随"（OPERATOR B3 已这样判断）；Sizing 行的 "≈ 5.5 k tokens" 与本轮估算 6.9 k 不一致，应用 API `count_tokens` 实测一次后钉死，或删掉这个未验证数字。
6. **"lessons 文件是跨会话记忆"**：`tasks/lessons.md` 自 05-09 无新增，而 MEMORY.md + claude-mem-lite 两层记忆已接管该职能。§10-R 的 "Read at session start" 每会话付一次读取，4 个月零回报。
