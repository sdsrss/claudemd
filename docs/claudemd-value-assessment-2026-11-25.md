# claudemd 到底有没有用 — 装与不装的对照实验 + 现场数据，2026-11-25

> 问题（用户原话）：模型越来越强，这个项目有没有在编程过程中被调用，有没有提高质量和效率，会不会装了反而不如不装。
> 证据三类：① 新做的受控对照实验（216 次 `claude -p` 运行，隐藏测试判分）；② 本机遥测 `~/.claude/logs/claudemd.jsonl`（10-22 → 11-25，12,893 行）；③ 会话转录（11-01 → 11-25，6 个项目，67,638 次请求）和各仓库 git / GitHub。
> 之前的分析（11-02、11-03、11-10、11-20）量的是闸门准不准、条文有没有被执行、流程成本；**从没在真实编码任务上比过"装 vs 不装"的结果**。11-03 报告原话："规范本身有没有让 Claude 写得更好，测不出来"。本文补的就是这一块。
> 脚本、预注册和原始数据：`tasks/claudemd-value-2026-11-25/`（gitignored）。

## 0 结论

| 问题 | 回答 | 依据 |
|---|---|---|
| 有没有被调用 | **有，而且每个会话都在起作用**：34 天里 hook 触发 12,893 次，拦截 278 次，注入规范模块 125 次；24 KB 核心规范进入每个主会话和子代理 | §2 |
| 有没有提高代码质量 | **受控实验里没有**：装与不装隐藏测试通过率都是 65/72（90.3%），差 0（95% 区间 −10.3 ~ +10.3 个百分点）。规范针对的几种行为（不改测试、如实报告已有红测试、在根因处修、同步文档、不越界改动），不装插件的 Opus 5.5 也全部做到，两组数字相同；唯一差别是装了之后验证证据更扎实（K5 回基线核实 7/8 vs 0/8），代码结果不变 | §3 |
| 有没有提高效率 | **没有，规范文字让它变慢变贵**：每个任务成本 ×1.83（规范作为仓库里的 CLAUDE.md 送达）到 ×2.44（作为系统提示送达，模型照做得更彻底）。**只装 hook 不装规范**：成本 ×1.04（0.99–1.10），等于不花钱 | §3、§8 |
| 照做得越彻底越好吗 | **不是**：规范被更严格执行时（§8 的 Cx 组），隐藏测试通过率从 65/72 降到 60/72（−6.9 个百分点，95% 区间 −11.1 ~ −2.8），原因是"旁边的缺陷写进遗留、不进本次改动"这条规则让模型故意不修同一个 bug 的另一条路径 | §8 |
| 精简版行不行 | 2.5 KB 的精简草稿：正确率与不装相同（66/72），成本 ×1.17–1.26，提交和三段式汇报在系统提示送达时 72/72。**没过我事先定的成本线（≤1.15×）**，差的那部分就是提交和汇报本身的开销 | §8 |
| 现场有没有真实收益 | **有，但集中在两个 hook**：推送到红 CI 前拦截（ship-baseline），34 天 20 次，11-03 以来 10/10 是真红（逐个 `gh run view` 核实，此前 21/23）；§8 删除变量拦截是保险：本期 191 次，11-03 逐条核查过的 254 次里没有一例能证明变量当时为空 | §4 |
| 现场最大的成本 | **规范规定的流程**：每版必须独立评审——评审子代理占 claude-mem-lite / code-graph-mcp 输入 token 的 33–36%、输出的 44–46%；记录类文件占新增行数 42–52%；82–95% 的汇报带"遗留"清单（中位 5–12 条），下一个会话再粘贴回来做 | §5 |
| 装了会不会反而更差 | **hook 部分不会**（几乎零成本，有真实拦截）；**规范文字部分在当前模型上是净负**：结果相同、多花约 80% 的钱和 66% 的时间，现场还驱动了大量流程性工作 | §6 |

**一句话判断**：项目不是白做，但它的价值已经缩到一小块——几个拦截真实风险的 hook。占项目大部分体量和维护精力的规范文字（24 KB 核心 + 9 个模块 + 围绕它的测量和发版），在 Opus 5.5 上测不出质量收益，却有可测的成本。继续做的方向应该是"薄的安全网 + 用结果实验把关"，不是"更完整的规范"。

## 6 判断

1. **被调用了吗？** 是。每个会话都在加载、注入、拦截。
2. **提高质量了吗？** 在 9 类针对规范设计的编码任务上，没有可测的提高。根本原因：**规范要求的那些好习惯，Opus 5.5 不装插件也已经做到了**（§3.3 除 K5 验证方式一行外，两组相同）。规范确实让验证证据更扎实（K5：基线核实 7/8 vs 0/8），但没有改变代码结果。以前的 A/B（10-15 的 C 组 "先复现 4/10 vs 10/10"）量的是"有没有照流程做"，本次量的是"代码对不对"——流程变了，结果没变。
3. **提高效率了吗？** 反方向。规范文字让每个任务贵 1.83 倍、慢 1.66 倍；现场的发版评审和遗留循环占了几个插件仓库约三分之一的 token、一半的新增行。
4. **装了反而更差吗？**
   - **hook：不会。** 成本 1.04×（统计上和不装分不开）；推到红 CI 的拦截 34 天 20 次，11-03 以来 10/10 真红；删除保险每次只多一次重试。这部分值得留。
   - **规范文字：对你的目标是净负。** 结果一样，多花 80% 的钱和 66% 的时间，还驱动了大量流程性工作。少数条目是你明确要的（中文回复、每次改动自动提交、三段式汇报、push/tag 前要你同意），这些可以留，用很短的文字就够。
5. **这个结论的边界**（不要过度引申）：
   - 实验任务是单回合、10 秒到 2.5 分钟、JavaScript。长会话、压缩、跨会话交接、多天发版、真正危险的删除，实验里没有。这些地方规范**可能**有价值，但现在没有任何数据支持，也没有数据否定。
   - 任务对 Opus 5.5 偏容易（不装时 90% 全过），更难的任务上规范有没有用，这次测不到。不过任务是专门挑规范声称有用的场景设计的，模型在每一项上都已经达标。
   - 任务和判分由同一个人（我）设计；隐藏测试是客观的；K5 两组 16 份汇报全部人工看过，K1 抽看 3 份，与正则判定一致。
   - 沙箱里 banned-vocab hook 找不到转录，静默放行（现场 0 次这种情况）；它现场 34 天只拦 2 次，对比较没有影响。

## 7 建议

按优先级。所有涉及规范文字和发版规则的改动都是 L3（会改变已发布插件的默认行为），需要你拍板。

## 8 第二轮：精简版对照，以及规范放在哪里会改变结果（同日补充）

用户选了 §7 的方案 (a) 之后，按预注册附录 2 跑了精简草稿（`tasks/claudemd-value-2026-11-25/lean/CLAUDE.md`，2,574 B，只留语言、先问清单、提交与核实、安全底线、三段式汇报、发版前读 ship 模块）。

### 8.1 发现的测量问题

带规范的各组里，规范是仓库根目录的 `CLAUDE.md`。模型习惯先 `cat CLAUDE.md`（不装的 V 组也在 30/72 次里试，只是读不到），在 C 组就读到了整份规范。真实使用时规范在 `~/.claude/`，不在仓库里。`.claude/CLAUDE.md` 和父目录的 CLAUDE.md 在 `--setting-sources project` 下都不加载（探测过），所以补跑了 **Cx / Lx**：规范用 `--append-system-prompt-file` 送达，套上 Claude Code 给 CLAUDE.md 的同一段包装文字；hook 用 `--settings` 从仓库外传入。预注册附录 3 写于补跑之前。

### 8.2 结果（每组 72 次，V 组同一批）

| 组 | 送达方式 | 隐藏测试全过 | 成本 / V | 耗时 / V | 本地提交 | `## 汇报` |
|---|---|---:|---:|---:|---:|---:|
| V 不装 | — | 65/72 | 1 | 1 | 0/72 | 0/72 |
| C 现行规范 | 仓库里的 CLAUDE.md | 65/72 | 1.83×（1.67–2.03） | 1.66× | 46/72 | 46/72 |
| **Cx 现行规范** | 系统提示 | **60/72** | **2.44×（2.35–2.58）** | 2.18× | 72/72 | 72/72 |
| L 精简草稿 | 仓库里的 CLAUDE.md | 66/72 | 1.17×（1.09–1.22） | 1.14× | 41/72 | 41/72 |
| **Lx 精简草稿** | 系统提示 | **66/72** | **1.26×（1.22–1.32）** | 1.28× | **72/72** | **72/72** |

- **送达方式本身会改变行为**：同一份现行规范，作为系统提示时提交和汇报从 46/72 变成 72/72，成本从 1.83× 变成 2.44×。真实使用时规范走的是 CLAUDE.md 通道（C 的通道），但没有可以 `cat` 的文件。真实情况应该在两者之间，所以本文的成本结论按区间报：**现行规范 1.8–2.4×，精简版 1.2–1.3×**。
- **现行规范照做得越彻底，结果越差**：Cx 在 K2 只有 4/8。没过的 4 次都修好了 `getUser`，却故意不碰 `getUsers`（汇报原话："缓存里仍然存原始行，所以 `getUsers` 的行为不受影响"），而 `getUsers` 正是用户报告的那个症状的另一条路径。这是现行 §0 / §1"旁边的缺陷写进遗留、不进本次 diff"规则的直接后果。K1 也一样：Cx 0/8 修好，V 1/8。
- **精简版没有这个副作用**：Lx 在 K2 修好 8/8，其余任务和不装完全一样；规范针对的副指标（保留断言、说明红测试、修根因、同步 README、改动范围）五组全部相同。

### 8.3 按预注册标准判定精简版

| 标准（附录 2） | 线 | L（仓库文件） | Lx（系统提示） |
|---|---|---|---|
| 成本 / V | ≤ 1.15× | 1.17× ✗ | 1.26× ✗ |
| 隐藏测试 | ≥ 62/72，K1 以外每项 ≥ 7/8 | 66/72 ✓ | 66/72 ✓ |
| 本地提交 | ≥ 46/72 | 41/72 ✗ | 72/72 ✓ |
| `## 汇报` | ≥ 46/72 | 41/72 ✗ | 72/72 ✓ |

**按事先定的线，精简版没有通过。** 差在成本，而多出的那部分就是提交和结构化汇报本身：Lx 比 V 多 1–2 轮（`git add` / `commit`）、输出 token 多 21%（3,492 对 2,877）、测试多跑一次（中位 2 对 1）。只装 hook、什么规范都不要（H 组）是 1.04×，但没有提交，也没有三段式汇报。这条线是我事先估的，没把"提交 + 汇报"本身的开销算够；要不要接受这 20–25% 换提交和汇报，由用户决定，我不在看到数据后自己改线。

第二轮花费：L $13.42、Cx $28.29、Lx $14.27；两轮合计（含试跑）$110.26。

在这批任务上，精简版在每一项上都不差于现行规范：成本低 36–48%（1.17–1.26× 对 1.83–2.44×），正确率相同或更高（66/72 对 60–65/72），提交和汇报的出现率相同或更高。
